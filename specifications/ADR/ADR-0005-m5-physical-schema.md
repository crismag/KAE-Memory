# ADR-0005 — Physical schema for the M5 persistent-memory proof

- **Status:** accepted
- **Date:** 2026-07-27
- **Closes:** OQ-010
- **Scope:** revision `0002`, additive. Not the final platform schema.

## Context

M5 must prove exactly one thing:

> A project is created, a user interaction is recorded, one AgentRun writes
> confirmed knowledge, that process ends, and a later AgentRun retrieves the
> knowledge from CockroachDB.

Revision `0001` already created `knowledge_items` and `knowledge_versions`. They
remain the authoritative durable memory and are **not modified**. Projects,
sessions, messages, agent runs, and relationships have no persistence.

This decision covers only what the proof above requires. Vector columns and
semantic indexes are an additive later revision and must not contaminate this
schema — see "Explicitly deferred".

## Decision

Add revision `0002` with six new tables:

```text
projects
   ├── sessions
   │      ├── messages
   │      └── agent_runs
   │
   ├── knowledge_items          existing, unchanged
   │      └── knowledge_versions existing, unchanged
   │             └── knowledge_provenance_links
   │
   └── knowledge_relationships
```

Five are as proposed. The sixth, `knowledge_provenance_links`, is added for the
reason given under "Provenance chain" below.

`agent_runs` is created before `messages`, because `messages.agent_run_id`
references it.

### Identifier types — a correction to the proposal

The proposal specifies `UUID` foreign keys to
`knowledge_items(knowledge_item_id)`. That column does not exist. Revision `0001`
created:

| Existing column | Type |
| --- | --- |
| `knowledge_items.id` | `STRING(64)` primary key |
| `knowledge_items.project_id` | `STRING(64)`, indexed, no foreign key |
| `knowledge_versions.id` | `INT` **autoincrement** primary key |
| `knowledge_versions.actor_id`, `execution_id` | `STRING(64)` |

Three consequences, resolved rather than papered over:

1. **Foreign keys into `knowledge_items` must be `STRING(64)`, targeting `id`.**
   New tables use `UUID` for their own primary keys as recommended; references to
   the existing knowledge tables use `STRING(64)` holding canonical UUID text.
2. **No database-level foreign key from `knowledge_items.project_id` to
   `projects.project_id`** — the types differ. Project ownership of knowledge is
   enforced in the application layer for M5. Aligning the types is an optional
   later revision `0003` (`ALTER ... TYPE UUID USING project_id::UUID`) while
   data volume is trivial; it is not required for the proof and is not done here.
3. **`knowledge_versions.id` is an autoincrement integer** — the distributed
   hotspot pattern this decision otherwise forbids. It is inherited from `0001`,
   is not on the write-hot path for M5, and is left alone. It is recorded as a
   known deviation, not endorsed. No new table repeats it.

Every new primary key is a `UUID` generated by the application, not by a database
sequence.

### projects

Durable aggregate boundary. All sessions, runs, and knowledge scope to it.

| Column | Type | Notes |
| --- | --- | --- |
| `project_id` | `UUID` | primary key |
| `project_key` | `STRING` | not null, unique, human-readable |
| `name` | `STRING` | not null |
| `description` | `STRING` | nullable |
| `status` | `STRING` | not null — `active`, `archived` |
| `created_at`, `updated_at` | `TIMESTAMPTZ` | not null |

No embedded workflow state.

### sessions

| Column | Type | Notes |
| --- | --- | --- |
| `session_id` | `UUID` | primary key |
| `project_id` | `UUID` | not null → `projects` |
| `session_type` | `STRING` | not null — `discovery`, `architecture`, `review` |
| `status` | `STRING` | not null |
| `started_at` | `TIMESTAMPTZ` | not null |
| `ended_at` | `TIMESTAMPTZ` | nullable |
| `created_at` | `TIMESTAMPTZ` | not null |

`session_type` is a plain string validated in the domain layer, so a future role
does not require a migration.

### agent_runs

The most important new table.

| Column | Type | Notes |
| --- | --- | --- |
| `agent_run_id` | `UUID` | primary key |
| `project_id` | `UUID` | not null → `projects` |
| `session_id` | `UUID` | nullable → `sessions` |
| `agent_role` | `STRING` | not null — `requirements`, `architecture`, `review` |
| `status` | `STRING` | not null — see below |
| `idempotency_key` | `STRING` | not null |
| `attempt_number` | `INT8` | not null, default 1 |
| `input_context` | `JSONB` | not null, default `'{}'` |
| `output_summary` | `JSONB` | not null, default `'{}'` |
| `continuation_state` | `JSONB` | not null, default `'{}'` |
| `started_at`, `completed_at`, `failed_at` | `TIMESTAMPTZ` | nullable |
| `error_code`, `error_message` | `STRING` | nullable |
| `created_at`, `updated_at` | `TIMESTAMPTZ` | not null |

`UNIQUE (project_id, idempotency_key, attempt_number)`.

**Statuses.** The database accepts `pending`, `running`, `succeeded`, `failed`,
`cancelled`, plus `interrupted` and `abandoned`, which
[`AGENT_EXECUTION_MODEL.md`](../AGENT_EXECUTION_MODEL.md) requires for lease
expiry and retry-budget exhaustion. `cancelled` and `abandoned` are both terminal
and distinct: cancelled is a human act, abandoned is budget exhaustion. Status is
a string validated in the domain layer, not a database enum.

**What must not be stored here:** complete model prompts, credentials, or raw
provider responses. Store retrieved knowledge identifiers, retrieval parameters,
checkpoint and continuation information, result references, a bounded output
summary, and typed failure information.

`agent_runs` records that an execution happened. It does **not** own knowledge.

### messages

Immutable interaction evidence.

| Column | Type | Notes |
| --- | --- | --- |
| `message_id` | `UUID` | primary key |
| `project_id` | `UUID` | not null → `projects` |
| `session_id` | `UUID` | not null → `sessions` |
| `agent_run_id` | `UUID` | nullable → `agent_runs` |
| `sequence_number` | `INT8` | not null |
| `actor_type` | `STRING` | not null — `user`, `agent`, `system` |
| `actor_id` | `STRING` | nullable |
| `message_type` | `STRING` | not null — `input`, `question`, `answer`, `proposal`, `confirmation`, `review_finding` |
| `content` | `STRING` | not null, stored verbatim |
| `metadata` | `JSONB` | not null, default `'{}'` |
| `created_at` | `TIMESTAMPTZ` | not null |

`UNIQUE (session_id, sequence_number)`.

Messages are immutable. A correction creates a new message and possibly a new
knowledge version; it never edits history.

### knowledge_relationships

A table, not JSONB arrays.

| Column | Type | Notes |
| --- | --- | --- |
| `relationship_id` | `UUID` | primary key |
| `project_id` | `UUID` | not null → `projects` |
| `source_knowledge_item_id` | `STRING(64)` | not null → `knowledge_items(id)` |
| `target_knowledge_item_id` | `STRING(64)` | not null → `knowledge_items(id)` |
| `relationship_type` | `STRING` | not null |
| `created_by_agent_run_id` | `UUID` | nullable → `agent_runs` |
| `metadata` | `JSONB` | not null, default `'{}'` |
| `created_at` | `TIMESTAMPTZ` | not null |

`UNIQUE (source_knowledge_item_id, target_knowledge_item_id, relationship_type)`
and `CHECK (source_knowledge_item_id <> target_knowledge_item_id)`.

Relationships are directed. Types: `depends_on`, `refines`, `conflicts_with`,
`supports`, `derived_from`, `implements`, `reviews`. Symmetric meanings such as
`conflicts_with` are handled by application rules rather than duplicated rows.

The domain's existing `RelationshipType` enum uses a different vocabulary
(`supports`, `contradicts`, `derives_from`, `implements`, `validates`,
`supersedes`, `blocks`). Because the column is a plain string, reconciling the
two is a domain-layer task in M5, not a migration. It must be reconciled — two
vocabularies for one concept is exactly the drift the terminology table forbids.

### knowledge_provenance_links

**This table is an addition to the proposed five.** The proposal said to add it
only if the existing provenance model cannot represent the M5 proof. It cannot,
for two reasons:

1. **Message → knowledge cannot be expressed.** `Provenance` carries `source`
   (free text), `actor_id`, and `execution_id`. FR-004 requires each candidate to
   resolve to the message that produced it. The only place to put a message
   identifier is `source`, overloading a descriptive field with a foreign key —
   unqueryable in practice and precisely the "parsing opaque values" the approval
   criteria forbid.
2. **"Which run *used* a piece of knowledge" cannot be answered.** `execution_id`
   records the run that *produced* a version. Consumption — the Architecture
   Agent reading confirmed requirements — would live only in
   `agent_runs.input_context` JSONB, which the approval criteria rule out.

| Column | Type | Notes |
| --- | --- | --- |
| `provenance_link_id` | `UUID` | primary key |
| `project_id` | `UUID` | not null → `projects` |
| `knowledge_item_id` | `STRING(64)` | not null → `knowledge_items(id)` |
| `knowledge_version_number` | `INT8` | nullable; null means the item as a whole |
| `agent_run_id` | `UUID` | nullable → `agent_runs` |
| `message_id` | `UUID` | nullable → `messages` |
| `link_type` | `STRING` | not null — `produced_by`, `used_by`, `derived_from_message` |
| `source_type`, `source_reference` | `STRING` | nullable, for non-message sources |
| `created_at` | `TIMESTAMPTZ` | not null |

Revision `0001` is untouched: this is an additive side table keyed by
`(knowledge_item_id, knowledge_version_number)` rather than a foreign key onto
`knowledge_versions.id`.

**Provenance chain:**

```text
message -> processed by agent_run -> produces knowledge version
        -> knowledge item participates in relationships
```

## Indexes

```text
sessions                  (project_id, started_at DESC)
messages                  (session_id, sequence_number)
messages                  (project_id, created_at DESC)
agent_runs                (project_id, created_at DESC)
agent_runs                (project_id, status)
agent_runs                (session_id, created_at DESC)
knowledge_relationships   (project_id, source_knowledge_item_id)
knowledge_relationships   (project_id, target_knowledge_item_id)
knowledge_provenance_links (knowledge_item_id, link_type)
knowledge_provenance_links (agent_run_id)
```

## CockroachDB choices

- Application-generated `UUID` primary keys. No monotonic integer keys — sequential
  insertion creates range hotspots in a distributed cluster.
- `TIMESTAMPTZ` everywhere. No naive timestamps. (The RA-01 rehydration defect was
  a symptom of this boundary being unenforced in the mapping.)
- `JSONB` only for open-ended metadata, input context, output summary, and
  continuation state. Anything joined, filtered, made unique, or driving lifecycle
  logic is a relational column.
- Every foreign key indexed; retrieval paths indexed as listed above.
- **No cascading deletion** of knowledge or run history. `ON DELETE` is omitted or
  `RESTRICT`. History is superseded, never removed.
- No database enums during this phase — vocabularies are validated in the domain
  layer so adding a value is not a migration.

## Explicitly deferred

- **Vector columns and semantic indexes.** M8, additive revision. M8 requirements
  must not contaminate this schema.
- Type alignment of `knowledge_items.project_id` to `UUID` (optional `0003`).
- Partitioning, multi-region topology, and locality clauses.
- Any change to revision `0001`.

## Approval criteria

Each answerable relationally, without process memory, log scraping, provider
transcripts, or parsing opaque JSON:

| Question | Answered by |
| --- | --- |
| What sessions belong to this project? | `sessions (project_id, started_at DESC)` |
| What messages occurred in a session, in order? | `messages (session_id, sequence_number)` |
| Which agent executions ran for the project? | `agent_runs (project_id, created_at DESC)` |
| What was the status and failure of a run? | `agent_runs.status`, `error_code`, `error_message`, `failed_at` |
| Which run produced or used a piece of knowledge? | `knowledge_provenance_links.link_type` |
| What current confirmed knowledge exists? | `knowledge_items.lifecycle` + latest `knowledge_versions.version_number` |
| How are two knowledge items related? | `knowledge_relationships` |
| Can a new process reconstruct context after the previous one ended? | `agent_runs.continuation_state` + `status` + provenance links |

## Consequences

**Positive.** The M5 proof is expressible in relational queries. Revision `0001`
is untouched and remains valid. Recovery state is durable, so a killed worker
loses nothing. No hotspot-prone keys are introduced. The schema does not
anticipate M8.

**Negative.** Two identifier conventions coexist — `UUID` for new tables,
`STRING(64)` for references into the existing knowledge tables — until an optional
`0003` aligns them. Project ownership of knowledge is enforced in the application
rather than by a foreign key. `knowledge_provenance_links` adds a sixth table
beyond the five proposed.

**Accepted risk.** Application-enforced referential integrity between
`knowledge_items.project_id` and `projects` can drift if a write path bypasses the
contracts. ADR-0004 already forbids such bypasses; this is one more reason the
MCP write boundary matters.
